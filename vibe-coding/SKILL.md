# Vibe Coding

目标：以尽可能少的沟通成本，把用户需求稳定地变成**正确、简洁、可维护、经过真实验证**的代码。

核心流程：

`理解需求 → 检查仓库 → 必要时澄清 → 复杂度分级 → 方案/Spec+Plan → 用户批准 → TDD → Review → 修复闭环 → QA → 完成`

## 0. 核心原则

1. **先读代码，再提问题。** 仓库能够回答的问题不要问用户。
2. **只问会改变实现方案的阻塞问题。** 不为命名、文件位置、内部实现细节向用户索取决定。
3. **按风险和影响范围分级，不机械按文件数量分级。** 文件数量只是重要参考。
4. **编码前只有一个 Approval Gate。** 用户批准方案后，自主执行到 Review 和 QA 完成；除非遇到重大新风险、不可逆操作或需求矛盾，否则不要反复请求确认。
5. **复杂任务先并行探索，再集中裁决。** 3 个 Subagent 使用相同角色、相同任务和相同上下文，彼此独立，不得读取其他方案。
6. **TDD 是默认实现方式。** 遵循 `RED → GREEN → REFACTOR`，测试不是事后补充。
7. **Review 和 QA 是质量门禁，不是报告阶段。** 发现问题必须修复、重测，直到通过。
8. **优先最简单的正确方案。** 避免无需求支撑的抽象、层级、框架和“顺手重构”。
9. **尊重现有架构。** 优先沿用仓库已有模式、约定、工具链和测试体系。
10. **Done = 验收标准通过 + 真实系统可运行。** “代码写完”或“单测通过”都不等于完成。

## 1. 理解需求与检查仓库

在提出问题或设计方案之前：

1. 阅读仓库级与目录级 Agent/开发说明，例如 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、README、架构文档。
2. 定位需求涉及的入口、调用链、核心模块、数据模型、配置和现有测试。
3. 搜索相似实现，优先复用仓库已有设计模式。
4. 确认构建、测试、Lint、类型检查和本地启动方式。
5. 对 Bug：先理解或复现现象，再判断根因；不要看到报错后直接打补丁。

不要无目的浏览整个仓库。只读取足够支撑当前决策的上下文。

### 需求澄清（Grill）

仅当存在**会显著改变行为、接口、数据或架构**的歧义时提问。

典型需要询问：

- 新旧 API / 数据是否要求兼容；
- 是否允许数据库或状态迁移；
- 不明确的业务规则、边界条件、权限或安全边界；
- 多个合理实现对应明显不同的产品行为；
- 用户未提供且仓库无法推断的外部约束。

不要询问：

- 函数、变量、文件如何命名；
- 应该放在哪个内部目录；
- 使用哪个现有 helper；
- 测试文件叫什么；
- 可以通过代码和文档自行判断的问题。

如果需要提问，优先一次提出少量高价值问题，而不是逐个追问。

## 2. 复杂度分级

依据 `references/complexity.md` 判定为 **简单 / 中等 / 复杂**。

快速原则：

### 简单

通常是局部、低风险、边界明确的改动，例如：

- 单模块小修复或小功能；
- 约 1–3 个文件；
- 不改变核心架构、持久化模型或公共契约；
- 回归面小且测试容易覆盖。

### 中等

通常涉及多个文件或模块，需要明确设计与验收，例如：

- 跨模块功能；
- 约 4–10 个文件；
- 局部 API / Schema / 状态行为变化；
- 有兼容性、回归或迁移考虑；
- 需要多层测试才能证明正确。

### 复杂

通常涉及系统级影响、高风险或明显不确定性，例如：

- 大范围跨层或跨系统修改；
- 通常超过 10 个文件；
- 核心架构、模块边界、数据所有权发生变化；
- 数据迁移、分布式、一致性、并发、事务、安全、权限、关键性能路径；
- 多个方案都有合理性，需要架构取舍；
- 失败成本高或回归范围大。

**任一高风险维度都可以直接升级复杂度，不受文件数量限制。**

## 3. 编码前方案与 Approval Gate

### 3.1 简单任务

向用户给出简洁方案摘要，至少说明：

- 根因 / 要解决的问题；
- 准备如何修改；
- 关键测试方式。

然后等待用户批准。

不要为简单任务制造冗长 Spec 文档。

### 3.2 中等任务

给出一份**可执行 Spec + Plan**，然后等待用户批准。

Spec 描述 **What / Why**，至少包含：

- Goal
- Scope
- Non-goals
- Behavior / Interface
- Constraints / Compatibility
- Acceptance Criteria

Plan 描述 **How**，至少包含：

- 主要修改步骤；
- 涉及模块或文件；
- 数据 / API / 配置变更；
- 测试策略；
- 验证顺序。

Acceptance Criteria 必须可验证，避免“功能正常”“性能良好”等不可执行表述。

### 3.3 复杂任务

按照 `references/parallel-planning.md` 执行。

必须并行召唤 **3 个相同角色的独立 Subagent**：

- 输入上下文尽量一致；
- 任务完全相同；
- 每个 Subagent 都把自己视为唯一负责该问题的高级工程师；
- 不要求“故意提出不同方案”；
- 彼此不得看到其他 Subagent 的方案；
- 每个方案都必须独立完整，可单独执行。

每个 Subagent 输出完整的：

1. 问题理解；
2. 技术方案；
3. 关键架构/设计决策；
4. 影响范围；
5. 风险与边界条件；
6. 测试策略；
7. Spec；
8. Plan。

主 Agent 是 **Judge + Synthesizer**，不是简单投票器。

主 Agent 必须比较至少：

- 正确性；
- 简洁性；
- 与现有架构的契合度；
- 可维护性；
- 兼容性；
- 实施和迁移风险；
- 可测试性；
- 是否存在遗漏的边界条件。

最终可以：

- 选择最强方案；或
- 综合多个方案中的最优部分。

只向用户提交**一个最终权威版 Spec + Plan**，简要说明关键取舍，然后等待批准。不要把三份原始方案全部倾倒给用户，除非用户要求。

---

## 4. 用户批准后的执行规则

用户批准方案后：

1. 将最终 Spec / Acceptance Criteria 视为实现基线。
2. 自主完成编码、测试、Review、修复和 QA。
3. 不因普通实现细节再次请求确认。
4. 如果实现过程中发现原方案存在重大错误、新的数据丢失风险、不可逆操作、安全风险或必须改变用户已批准的行为，停止该部分实现并向用户说明。
5. 不擅自扩大 Scope。

如果仓库要求保存设计文档，则将中等/复杂任务的最终 Spec 和 Plan 写入仓库规定位置；没有该约定时不要为了流程而制造永久文档。

## 5. TDD 实现

默认执行严格的短循环：

### RED

1. 从当前 Acceptance Criterion 选取最小行为切片。
2. 编写能够证明该行为的测试。
3. 运行测试并确认它因为目标能力尚未实现而失败，而不是因为测试本身错误。

### GREEN

1. 编写让当前失败测试通过的最小正确实现。
2. 不提前实现尚无测试驱动的假想需求。
3. 运行相关测试确认通过。

### REFACTOR

1. 在保持测试绿色的前提下清理实现。
2. 消除明显重复、过深嵌套、坏命名和不必要复杂度。
3. 优先简化，不为未来假想需求引入抽象。

然后进入下一条行为切片，重复 `RED → GREEN → REFACTOR`。

### 测试层级

按需求选择合适层级：

- Unit Tests：纯逻辑、边界条件、错误处理；
- Integration Tests：数据库、消息、文件、缓存、外部适配器等模块协作；
- Contract/API Tests：公共接口、序列化、兼容性；
- E2E / Behavior Tests：关键业务路径；
- Gherkin：复杂核心业务规则且项目已有或适合行为测试时使用。

禁止通过削弱、删除或篡改有效测试来让实现“通过”。如果测试与已批准 Spec 冲突，应先判断哪一方过时。

### 复杂任务的实现并行化

复杂任务可按需要使用 Subagent 实现，但不是强制要求。

适合并行的情况：

- 可清晰拆分的独立模块；
- 大规模重构中的独立工作流；
- 需要并行实验或验证不同实现细节。

存在代码写入冲突或并行实验时，优先使用 `git worktree` 隔离工作空间。

原则：

- 主 Agent 负责最终集成；
- 子任务边界必须清晰；
- 不让多个 Agent 同时修改同一核心文件；
- 集成后重新运行完整相关测试，不信任各 worktree 的局部成功。

## 6. 独立代码 Review

实现和相关测试通过后，召唤 **1 个独立 Subagent** Review 当前改动。

Reviewer：

- 不参与当前实现；
- 不修改代码；
- 阅读最终 Spec / Acceptance Criteria、完整 diff 和必要上下文；
- 以缺陷优先，返回具体、可操作的问题；
- 发现第一个问题后继续检查完整改动。

根据复杂度采用不同 Review 深度，细则见 `references/review.md`。

### 简单任务

执行 **Adversarial Review**：

重点尝试证明代码存在：

- Bug；
- Edge Case；
- Regression；
- 错误假设；
- 缺失测试。

### 中等任务

单个 Reviewer 同时执行两个视角：

1. **Spec Verifier**：是否正确、完整满足 Spec 和所有 Acceptance Criteria；
2. **Cleaner**：是否存在重复、死代码、坏命名、过深嵌套、无价值抽象和不必要复杂度。

### 复杂任务

单个 Reviewer 同时执行三个视角：

1. **Spec Verifier**；
2. **Cleaner**；
3. **Architect Review**：模块边界、依赖方向、耦合、数据所有权、扩展性和长期维护成本。

Cleaner 必须遵守：**Prefer simplification over abstraction.**

### Review 闭环

若发现有效问题：

`Review → 修复 → 相关测试 → 必要时新增回归测试 → 再 Review`

直到没有阻塞问题。

不要把 Reviewer 的意见机械视为正确；主 Agent 应结合 Spec、代码和测试判断其有效性。

---

## 7. QA 与真实验证

Review 通过后执行 QA。具体检查表见 `references/qa.md`。

至少执行：

1. Build / Compile；
2. Lint / Format / Type Check（项目存在时）；
3. 相关 Unit Tests；
4. 相关 Integration / Contract Tests；
5. E2E；
6. 按仓库正常方式启动真实服务或应用；
7. 发起真实请求 / UI 操作 / CLI 调用，验证关键主路径；
8. 检查响应、状态变化、持久化结果、日志和必要副作用；
9. 对照 Acceptance Criteria 逐项确认。

真实请求必须尽量走正式入口，不要只调用内部函数模拟成功。

如果环境限制导致某项无法执行：

- 明确说明未验证项及原因；
- 完成所有仍可执行的验证；
- 不把未执行的检查描述为“通过”。

### QA 闭环

若 QA 失败：

`QA Failure → Diagnose → 新增/修正测试 → Fix → Review（必要时）→ QA`

直到通过或明确被外部环境阻塞。

---

## 8. 完成标准

只有同时满足以下条件才可以宣布完成：

- 已批准的 Scope 已实现；
- Acceptance Criteria 全部满足；
- 相关自动化测试通过；
- Review 无未解决阻塞问题；
- 真实服务 / 应用已尽可能启动并完成主路径验证；
- 没有隐藏已知失败；
- 没有无关改动或明显临时代码。

最终汇报保持简洁，说明：

- 实现了什么；
- 关键设计决定；
- 测试与 QA 结果；
- 仍存在的外部限制或风险（如有）。

不要重复整份 Spec，也不要输出冗长工作日志。
