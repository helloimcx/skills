# 复杂度判定

复杂度用于决定规划、Review 和实现流程的重量。不要只按文件数量机械分类。

## 评估维度

| 维度 | 简单 | 中等 | 复杂 |
|---|---|---|---|
| 影响范围 | 单点/单模块 | 跨模块 | 跨层/跨系统 |
| 文件数量（参考） | 1–3 | 4–10 | >10 |
| 架构影响 | 无 | 局部设计变化 | 核心边界/依赖变化 |
| 公共接口 | 不变 | 局部变化 | 大范围契约/兼容性变化 |
| 数据 | 无变化 | Schema/状态局部变化 | Migration/所有权/一致性变化 |
| 风险 | 低 | 中 | 高 |
| 不确定性 | 明确 | 少量未知 | 多个未知/多方案取舍 |
| 并发/事务/安全 | 无 | 局部涉及 | 核心涉及 |
| 回归范围 | 很小 | 可控 | 广泛 |
| 验证难度 | 单测即可 | 多层测试 | 真实系统/多组件验证 |

## 升级规则

以下任一情况通常直接按复杂任务处理：

- 核心认证、授权、安全边界；
- 跨服务分布式一致性；
- 高风险并发或事务语义；
- 不可逆数据迁移；
- 核心公共 API 的破坏性变更；
- 核心架构或模块边界重构；
- 大范围性能关键路径变化；
- 失败可能造成数据丢失、严重业务中断或安全事件；
- 存在多个重大技术路线且需要权衡。

## 降级原则

大量文件并不必然复杂。例如批量机械字段改名、生成代码更新、格式迁移，如果：

- 行为规则单一；
- 修改高度机械；
- 风险低；
- 自动化验证充分；

可以按中等甚至简单任务执行。

## 判定输出

内部判断时用一句话说明原因即可，例如：

- `简单：仅修改单模块 2 个文件，无公共接口变化。`
- `中等：跨 API/Service/Repository，涉及兼容行为和集成测试。`
- `复杂：虽只预计 3 个文件，但涉及认证边界与并发状态一致性。`
