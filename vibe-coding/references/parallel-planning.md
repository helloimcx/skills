# 复杂任务：3-Agent 独立规划协议

目标不是角色分工，而是对同一复杂问题做 **3 次独立高质量求解**，扩大方案搜索空间，再由主 Agent 集中裁决。

## 1. 前置条件

主 Agent 先完成：

1. 仓库检查；
2. 阻塞歧义澄清；
3. 相关上下文收集；
4. 约束、现状架构和验收目标整理。

不要让三个 Subagent 各自重新漫无目的扫描整个仓库；给它们足够且尽量一致的上下文，同时允许它们按需要读取更多代码验证判断。

## 2. 独立性要求

三个 Subagent：

- 使用相同角色；
- 接收相同问题；
- 接收相同核心上下文；
- 不得查看其他 Subagent 的输出；
- 不得相互讨论；
- 不得以“提出一个与其他人不同的方案”为目标；
- 都应把自己视为唯一对最终方案负责的高级工程师。

这样得到的是独立采样，而不是为了多样性制造差异。

## 3. 建议委派 Prompt

可按环境能力调整措辞，但保持语义：

> 你是负责本任务的高级软件工程师。请独立分析需求和提供的仓库上下文，给出你认为最正确、简单、可靠、可维护的完整实现方案。不要假设有其他 Agent 会补充你的工作，也不要为了追求差异而刻意设计另类方案。
>
> 输出必须包含：
> 1. 问题理解与关键假设
> 2. 技术方案
> 3. 架构/设计决策及理由
> 4. 预计影响的模块/文件
> 5. 兼容性、迁移、边界条件和主要风险
> 6. 测试策略
> 7. 可执行 Spec（Goal / Scope / Non-goals / Behavior / Constraints / Acceptance Criteria）
> 8. 可执行 Plan（按实施顺序）
>
> 优先复用现有架构，避免无需求支撑的抽象和 Scope 扩张。

## 4. 主 Agent 裁决

三个方案返回后，不进行多数投票。

主 Agent逐项比较：

1. **Correctness**：能否完整满足需求；
2. **Simplicity**：是否存在更小、更直接方案；
3. **Architecture Fit**：是否符合现有模块边界和依赖方向；
4. **Maintainability**：长期维护成本；
5. **Compatibility**：旧接口、旧数据、调用方影响；
6. **Risk**：迁移、并发、事务、安全、性能等风险；
7. **Testability**：是否容易用自动化测试和真实 QA 证明；
8. **Completeness**：是否遗漏关键边界条件或回滚策略。

重点关注方案之间的**分歧点**。如果 A/B/C 在某个核心假设上不一致，主 Agent 必须通过代码、文档或进一步分析解决，而不是凭直觉选择多数意见。

## 5. 综合规则

允许：

- 完整采用最强方案；
- 采用 A 的总体架构 + B 的迁移策略 + C 发现的边界条件；
- 推翻三个方案并提出更优综合方案，但必须能说明依据。

禁止：

- 2:1 多数票直接决定；
- 把三个方案简单拼接导致重复或矛盾；
- 为照顾每个 Subagent 而保留不必要设计；
- 把三份完整原始输出直接交给用户代替主 Agent 决策。

## 6. 最终输出

主 Agent 只形成一个权威版本：

### Final Spec

- Goal
- Scope
- Non-goals
- Behavior / Interfaces
- Constraints / Compatibility
- Acceptance Criteria

### Final Plan

- 有顺序的实现步骤
- 主要模块/文件
- 数据/API/配置变化
- 测试计划
- QA 计划

最终方案保持结论先行、简洁、清晰、易懂。附一小段“关键取舍”，只解释真正影响设计的决策。

同时附一张紧凑的 Mermaid 或 ASCII 方案示意图，展示目标入口、关键模块或数据流及预期结果；用户批准后将该图保留在 Plan 文档中。

然后进入唯一一次用户 Approval Gate。
