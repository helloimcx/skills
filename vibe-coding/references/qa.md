# QA 检查表

QA 的目标是证明**真实系统工作**，而不是只证明代码能够被测试框架调用。

根据项目实际情况执行适用项。

## 1. 静态质量门禁

- Build / Compile
- Format
- Lint
- Type Check
- 代码生成结果是否最新（若项目要求）

## 2. 自动化测试

按从快到慢顺序：

1. 修改点相关 Unit Tests；
2. 相关模块 Test Suite；
3. Integration Tests；
4. Contract / API Tests；
5. E2E / Behavior Tests；
6. 必要时完整测试套件。

任何测试失败都要区分：

- 本次修改造成的回归；
- 测试/环境本身故障；
- 已存在失败。

不要静默忽略失败。

## 3. 启动真实服务

使用项目正常运行方式，例如：

- 项目原生启动命令；
- Docker Compose；
- 本地开发环境；
- 仓库提供的测试/预览服务。

验证：

- 进程正常启动；
- 无关键初始化错误；
- 依赖连接成功；
- Migration 正常（如有）；
- 健康检查正常（如有）。

## 4. 真实主路径

尽可能从用户真实入口验证：

- HTTP/gRPC：发送真实请求；
- CLI：执行真实命令；
- Web：完成关键 UI 操作；
- Worker/Queue：投递真实测试消息并观察消费；
- 数据处理：使用代表性输入跑完整流程。

检查：

- 返回值 / 状态码；
- 数据库或持久化结果；
- 事件、消息或异步副作用；
- 日志中是否有隐藏异常；
- 幂等、错误路径或回滚（当需求涉及）。

## 5. Acceptance Criteria

最终逐条检查所有 AC：

- `[PASS]` 有明确验证证据；
- `[BLOCKED]` 因环境限制无法验证，并说明原因；
- 不允许没有执行验证却标记 `[PASS]`。

## 6. QA 失败处理

发现失败后：

1. 最小化复现；
2. 判断根因；
3. 优先写能够捕获该问题的回归测试；
4. 修复；
5. 重新执行相关测试；
6. 必要时重新 Review；
7. 重跑真实 QA。
