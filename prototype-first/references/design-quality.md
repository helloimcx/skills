# 设计品质与截图自审

每次设计或修改原型前阅读本文件。目标是让用户看见内容就知道如何行动；视觉精致与操作直观必须同时成立。

## 1. 先明确用户要完成什么

从需求和现有产品提炼：谁在什么场景使用、当前页面解决什么问题、主要动作是什么、完成后用户看到什么。通常用几句话即可，不要求另写方案等批准。

按真实任务组织信息与步骤，使用领域内用户熟悉的词。先展示决策需要的信息，次要信息就近渐进展开；不要为了减少屏幕元素而把高频操作藏进菜单。保留任务必要的信息密度，避免过度留白把内容推到屏幕外。

## 2. 视觉：简洁、美观、大气

- **层级**：首屏呈现页面用途、核心内容与下一步；同一任务区域通常只有一个视觉上最突出的主操作，次要与危险操作区分。多个独立任务可各有入口，避免满屏争抢注意力。
- **排版**：用一致的栅格、间距与对齐组织内容。沿用项目 tokens；没有时建立少量字体层级、间距、圆角和颜色变量，统一使用。字号、行高与内容宽度便于阅读，长标题和中文内容不挤压操作。
- **色彩与材质**：以适合产品的中性色和克制的强调色突出内容；颜色传递明确语义。避免无意义渐变、大面积模糊、叠层阴影、满屏卡片、装饰图标或超大标题削弱信息层级。必要的装饰应服务品牌和内容。
- **一致性**：同类操作的位置、样式、名称与状态一致。优先目标平台熟悉的导航和控件，不把 Web 产品强行做成 iOS 设置页，不擅自替换现有品牌。
- **内容**：使用长度和分布接近真实业务的数据，至少考虑长标题、长数值和稀疏内容。原型说明置于注释、README 或弱化的评审标识，不在产品主流程堆放实现细节。

## 3. 交互：Don't Make Me Think

- **可发现**：按钮像按钮，链接像链接，选中项和当前位置明显。关键动作不只依赖 hover、手势或用户猜测；不明确的图标附可见文字。不要用长篇说明补救难懂的界面。
- **可预期**：文案说明动作与对象，例如“创建项目”“保存修改”；导航回答“去哪里”，提交回答“会发生什么”。输入有持久标签，默认值合理，单位和必填条件明确。
- **有反馈**：点击后立即有可感知变化；异步操作展示处理中和完成结果，避免重复提交。反馈靠近发生处，保留页面上下文，不为每次轻操作弹确认框。
- **可恢复**：可返回、可取消；失败说明原因与可执行的恢复方式，并保留输入。破坏性或不可逆动作依实际后果提供确认或撤销，原型只模拟结果。
- **状态完整**：按本次任务覆盖默认、加载、空、成功、错误、禁用等适用状态；不适用说明原因。主操作及主路径中的返回、取消、重试等入口必须有真实的本地反馈，不留空点击或 `href="#"` 充数。评审用状态切换放在独立评审区或参数中，不伪装为产品功能。
- **输入与无障碍**：使用语义化控件、可见焦点、合理 Tab 顺序与键盘操作；弹层管理焦点、可关闭、关闭后回到触发点。不能只用颜色区分状态；文字有足够对比度，触控目标和布局遵循目标平台规范，窄屏、放大文字时内容仍可用。动效用于解释变化，尊重减少动态效果偏好。

## 4. 截图—自问—修正—复查（必做）

### 获取真实证据

1. 用可用浏览器工具打开实际 HTML 或本地预览地址，等待字体、资源和布局稳定。针对本次改动确定主路径和相关状态，实际点击和键盘操作并观察结果。
2. 截取主视图的首屏与主路径关键状态，例如提交结果、弹层或校验错误。长页面可补全页截图，但全页缩略图不能替代首屏检查。
3. 在目标视口截图；响应式页面至少覆盖桌面和窄屏（例如 1440×900、390×844，实际尺寸按产品确定）。专属固定终端用其真实尺寸，说明不适用的范围。检查窄屏溢出、遮挡、操作可达性，并用长内容和文字放大补查布局。
4. 使用图像查看能力实际查看每张截图。可放大检查局部，但不能裁掉问题区域来宣称通过。截图来源必须是当前原型实际渲染，不能拿生成图片、设计参考图或旧版画面代替。

截图可保存在原型目录 `drawings/`，或项目约定的可交付位置；按页面、视口、状态、轮次命名。自审记录应链接最终版本截图，注明文件/版本、视口、状态及交互走查结果；废弃轮次是否保留遵循项目惯例，不要求无止境归档。

### agent 必须逐项自问

站在首次使用者视角，先看截图再结合操作结果回答以下问题；每项写“通过 / 不通过 / 未验证”，并给出具体画面或行为证据。不要只写“符合 Apple 风格”或“体验良好”。

| 自问 | 判断依据 |
|---|---|
| 第一眼能看懂这是什么页面、能完成什么吗？ | 标题、核心内容与当前状态直接说明用途，无需先读操作手册。 |
| 用户一眼能找到下一步、知道点哪里以及点后会发生什么吗？ | 主操作位置与层级明显，名称具体；关键入口不用猜图标或反复试点。 |
| 达到了简洁、美观、大气的品质吗？ | 对齐、留白、字体、配色与组件一致；装饰不抢内容，信息不拥挤也不空洞。指出实际视觉依据。 |
| 有没有让用户多想、多记、多走一步的地方？ | 没有模糊标签、冗余选择、重复输入或隐藏的高频功能；必要复杂信息有合理分组。 |
| 交互自然合理、反馈明确且能纠错吗？ | 实际走通主任务，观察到处理中/结果等适用反馈，验证相关的取消、返回、重试及输入保留。 |
| 不同尺寸和真实内容下仍然清楚、好操作吗？ | 对应截图中没有溢出、截断关键信息、遮挡按钮；长内容和文字放大后仍可用。 |
| 键盘与可读性是否达标？ | 结合截图检查文字、对比度和焦点，并实际验证 Tab、激活、弹层关闭和焦点恢复等适用行为。 |
| 是否还有需要向用户解释“这里其实应该……”才能使用的部分？ | 没有以解释、演示话术或假按钮掩盖设计缺口；尚未实现的模拟边界已如实注明。 |

“一眼理解”是 agent 的启发式自审判断，不能冒充真实用户测试或 Apple 官方认证。截图不能证明键盘操作、反馈时序和完整任务路径，这些必须实际操作验证；同样，操作成功也不能替代视觉审查。

### 修正与交付

- 有“不通过”就先修原型，重新走查受影响路径并截图、看图复查；最终记录引用修正后的证据。自审全部适用项通过后再请用户确认，不把明显缺陷留给用户发现。
- 连续三轮仍未通过时，停止盲目打磨，记录具体问题、已尝试修正和待决定的取舍，交付当前可点击原型与证据并明确标记“自审未通过”。不要写成已完成或自动进入实现；若取舍确需用户决定，再提出具体问题。
- 浏览器、截图或看图能力不可用时，先完成可做的设计与检查，写明限制和“未验证”，提供可复现的打开方式及待查项。不能虚构截图、隐去未验证项或把清单脚本通过算成视觉通过。
- 对用户简短报告：原型入口、关键截图、自审结论和剩余问题。自审状态与 README 的“待确认 / 已确认 / 已确认并实现”分开；自审通过仍不代表用户批准。

## 参考依据

Apple 的指导用于设计判断；上面的截图自问表和迭代上限是本 skill 的工作约定，并非 Apple 官方验收标准。

- [Apple Human Interface Guidelines：Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles/)：设计原则。
- [Apple Human Interface Guidelines：Layout](https://developer.apple.com/design/human-interface-guidelines/layout)：布局与层级。
- [Apple Human Interface Guidelines：Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)：可访问性。
- [Steve Krug：Don't Make Me Think](https://sensible.com/dont-make-me-think/)：以低认知负担检视易用性。

涉及具体平台尺寸、控件或新规范时查阅相应官方页面，避免把模板默认值当作通用平台标准。
