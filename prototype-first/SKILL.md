# prototype-first — 原型先行 UI 开发流程

**硬规则（批准门，不可跳过）：任何 UI 改动必须先改/先出 `design/` 下的可点击原型，经用户确认后，才允许动实现代码。** 未确认前写实现代码一律返工。

为什么：UI 改动的成本大头是「做完才发现交互不对」的返工。文字方案暴露不了交互问题；可点击原型用假数据把布局、状态、边界情况全部演出来，用户点过、确认过，实现照着做，返工最少。本流程源自 ai_quality_analysis `design/` 的生产实践（硬规则 1），已在 code-loop dashboard 复用验证。

## 设计品质要求

以 **Apple Human Interface Guidelines 的设计品质**和 **Don't Make Me Think 的低认知负担**为标准：界面简洁、美观、大气，交互自然合理，让首次使用的人一眼理解页面用途、主要操作和操作结果。

- 用清晰层级、留白、对齐、精炼文案和一致组件建立质感；内容优先，主次分明。
- 用用户熟悉的名称与控件表达操作；主任务入口可见，反馈及时，返回和纠错容易。
- 遵循目标平台、已有品牌与设计系统；不把“Apple 标准”等同于套用苹果外观、玻璃效果或装饰动画。
- **动手前阅读 [references/design-quality.md](references/design-quality.md)**，按其中的设计准则与截图自审执行。代码能运行、清单校验通过，都不能证明设计达标。

## 三段工作流

### 1. init（项目首次落地）

1. 沿用已有原型目录；没有时默认 `design/`，用户指定目录时从其要求。
2. 建目录：`README.md`（抄 [references/template-README.md](references/template-README.md)，填清
   单表）+ `assets/`（共享 css/js）。
3. **把硬规则写进项目 `AGENTS.md` / `CLAUDE.md` 硬规则区**（一行）：
   > `design/` 是唯一 UI 原型源：任何 UI 改动必须先改原型、经用户确认后才启动开发。
   不写进项目指令，下一个会话就不知道有这道门——这一步是流程跨会话生效的关键，不可省。
4. 跑 `python <skill目录>/scripts/check_design.py <design目录>` 确认 exit 0。

### 2. per-change（每次 UI 改动）

1. **确定主任务**：从现有需求中提炼目标用户、此页最重要的任务及最短操作路径；检查项目既有设计语言。按 design-quality 准则确定信息层级与必要状态，不增加无关功能。
2. **改原型**：新页参考 [references/template-page.html](references/template-page.html)，替换示例内容与交互，不把模板当作所有页面的固定布局；改既有页直接
   改；多视图大项目在「演进基座」完整副本上演示增量（见 conventions §9）。假数据内联页面
   `<script>`，视觉 token 与实现主题一致。
3. **清单自检**：`python <skill目录>/scripts/check_design.py <design目录>`——清单与磁盘不一致即红，先修。该脚本只校验清单，不评价视觉或交互。
4. **截图与交互自审**：在真实浏览器打开本次原型，走通主任务和相关状态；截取目标尺寸下的实际画面，**调用图像查看能力逐张看图**，按 design-quality 的自问表逐项回答“通过 / 不通过 / 未验证 + 证据”。发现问题先修原型，再重走受影响路径、重新截图复查；将结论写入原型目录 README 的自审记录。不能只生成截图、不看图，也不能凭源码宣称达标。
5. **请用户确认**：自审通过后，提供可访问的原型地址或 HTML 文件链接、关键截图和简短自审结论。截图作为评审证据，仍须交付可点击原型。**已有针对本次原型版本的明确确认则沿用；否则停在批准门等确认。** 缺少浏览器或看图能力时按 design-quality 记录“未验证”，如实交付待审材料，不能声称自审通过。
6. 确认后：README 状态列 `待确认 → 已确认`；spec/plan 的「关联」字段写明原型文件与确认事实。
7. 进入实现（走项目常规开发流程）；实现落地后回填 `已确认并实现（日期 + 对应实现入口）`。

### 3. check（改动前后各一次）

```bash
python scripts/check_design.py <design目录> [--quiet]
```

FAIL（exit 1）：缺 README / 缺清单表 / 缺「文件」或「状态」列 / 孤儿原型（盘上有清单无）/
幽灵行（清单有盘上无）/ 重复登记行 / 状态词汇非法 / 清单行「文件」列解析不到 .html 文件名。
WARN（不阻断）：页面缺 `<!-- proto:` 头注释 / README 引用 assets 未带 `?v=` 版本 pin。

## 状态词汇表（README 状态列唯一合法值）

| 状态 | 含义 |
|---|---|
| `待确认` | 原型已出/已更新，等用户看 |
| `已确认` | 用户拍板，开发可启动 |
| `已确认并实现` | 已落地（附日期）；原型保留为设计事实源 |

状态值后允许附括号备注（日期、走查结论等），校验只认前缀。

## 红线

- 不跳过原型直接写实现；不用文字方案/截图替代可点击原型。
- 不跳过实际截图、看图和交互走查；自审通过不等于用户确认，未验证项不能写成通过。
- 原型确认后不删除：它是该视图的设计事实源，后续改同一视图仍先改原型。
- 原型目录是设计资产不是运行时代码：产品服务不路由它，产品运行时测试不加载它；设计评审的浏览器走查与截图检查照常执行。
- 完整约定（命名、assets 版本 pin、演进基座、口径同步、与外部设计工具解耦）见
  [references/conventions.md](references/conventions.md)。
