# Project Setup

把一个新目录初始化成**最小、可运行、可测试、可复现、可持续演进**的软件项目。只负责项目冷启动和初始化验收；不要继续实现初始化范围之外的产品功能，也不要把“生产级”误解为预先加入数据库、缓存、消息队列、微服务或复杂框架。

本 skill 独立运行，不依赖其他开发流程或 skill。初始化完成并汇报结果后停止；后续功能开发属于新的任务。

## 1. 预检目标

在任何写入前：

1. 解析并明确目标的绝对路径，检查父目录和当前工作目录，避免在错误层级初始化。
2. 读取目标及父仓库中适用的 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、README、`docs/`、Git 状态和配置。
3. 将目标分类为：不存在、空目录、仅含用户认可的 bootstrap 文件、已有项目。
4. 不对已有项目运行通用脚手架。若用户明确要求为已有项目补齐工程基线，先做只读差距分析，再以增量方式保留现有架构、接口和文件。
5. 确认初始化范围：项目类型、语言/运行时、包管理器、公共入口、运行与分发方式、部署形态、数据/外部依赖、支持平台、许可证和关键非功能要求。

只有缺失信息会显著改变产品形态、技术兼容性、数据所有权、安全边界、部署或外部权限时才询问用户。用户已经给出明确技术栈和目标、且目标为空时，直接采用合理默认值继续。

当前版本、官方初始化命令、支持周期或安全状态不确定时，查阅当前官方文档或其他一手资料。保留用户指定的语言、框架、包管理器和部署选择；发现冲突时用证据说明。

## 2. 确定初始化蓝图

先阅读 [生产基线](references/production-baseline.md)。确定项目形态后，只读取 [项目形态](references/project-profiles.md) 中对应部分。在创建架构文档和跨 Agent 长期维护规则前，阅读 [架构治理初始化](references/architecture-governance.md)。

初始化蓝图至少明确：

- 一个可从公共入口验证的最小垂直切片；
- 源码、测试、配置、文档和构建产物的职责边界；
- 模块接口和单向依赖；
- 安装、运行、测试、构建和聚合验证命令；
- 适用的错误、日志、`trace_id`、安全以及外部失败策略；
- 可执行的初始化验收标准。

优先选择满足已知需求的最小架构。没有真实需求时，不加入数据库、Cache、MQ、容器、云资源、插件系统、通用仓储或多服务拓扑。

## 3. 安全初始化

按小步创建并随时验证：

1. 优先使用官方或生态标准脚手架，并记录生成器和运行时版本；没有合适脚手架时手工创建最少文件。
2. 禁止对非空目标静默使用 `--force`、清理、删除或覆盖。必须替换已有文件时，先明确精确目标和影响；不可逆或扩大范围的操作需要用户授权。
3. 使用项目本地工具链。遵循所选生态的锁文件规范：提交工具生成且具有真实解析/构建语义的锁文件；只有不存在可锁定依赖图且生态不产生有意义锁文件时才标记 `[N/A]`。不得手工创建注释或占位空锁。
4. 除非用户明确要求，不安装全局工具、不修改用户级配置、不创建远程仓库、云资源、外部账号、生产数据库或付费服务。
5. 创建最小公共入口和一条可观察行为。包含自定义行为时先写有效失败测试，再按 `RED → GREEN → REFACTOR` 实现；纯脚手架配置和文档使用结构、解析、命令或链接检查，不伪造代码级 RED。
6. 建立 Unit、Integration、E2E、Regression 的测试约定和聚合入口。只实现适用且有价值的层级；无真实边界或历史 Bug 时记录 `[N/A]`，不得用空断言、skip、ignore 或虚假基础设施凑数。
7. 创建并填写 `docs/architecture.md`、bootstrap Spec、bootstrap Plan 和必要 ADR，使 `docs/specs/`、`docs/plans/`、`docs/decisions/` 都由真实内容承载。按架构治理初始化契约，增量生成短小的根 Agent 路由、按需加载的维护策略、工具无关的初始历史、replaceable diagram provider manifest，以及 README 中的当前架构图；保留已有指令和文档内容。
8. 配置项目实际支持的 format check、lint、type/static check、tests、build、安全/依赖检查和单一聚合命令。已知 CI 平台时让 CI 调用同一聚合入口；未知时不要擅自绑定托管平台。
9. 在 README 中记录从干净 checkout 开始的安装、运行、测试、构建和验证命令，不依赖本机绝对路径、个人缓存或隐式全局工具。

初始化过程中发现缺陷时，先最小复现并定位根因；为真实缺陷增加 Regression Test 后修复，不叠加 workaround，也不为了绿色结果降低门禁。

## 4. 验证初始化结果

阅读并执行 [验证契约](references/verification.md)。至少：

- 从正式公共入口验证一个成功路径和一个关键失败路径；
- 运行所有适用的静态检查、测试、build/package 和聚合质量命令；
- 在干净环境验证安装、构建、测试与运行可复现；存在有意义锁文件时使用冻结/锁定模式；
- 检查循环依赖、重复、复杂度、Dead Code、临时代码、调试输出、Secrets 和生成物内容；
- 验证根 `AGENTS.md` 路由、Claude Code 的共享导入、架构维护策略、provider manifest、初始变更记录和 README 当前图相互一致；绘图 provider 不可用时使用声明的 fallback，不得静默安装或谎报验证成功；
- 对照初始化验收标准记录 `[PASS]`、`[FAIL]`、`[BLOCKED]` 或 `[N/A]` 及证据；未执行的检查不得标记为通过；
- 同步 README、架构、bootstrap Spec/Plan 和 ADR，使文档与真实产物一致。

如果完整测试或适用门禁失败，定位根因、补测试、修复并重跑。只有公共入口、完整自动化测试、适用门禁和文档一致性都得到证据支持时，初始化才完成。

## 5. 完成并停止

最终报告只需说明：

- 创建的项目和关键边界；
- 安装、运行、测试、构建、聚合验证命令；
- 验收证据和未解除的外部限制；
- 重要技术决策；
- 新项目的实际结构或主数据流。

不要在同一次初始化任务中继续开发额外业务功能。用户随后要求实现功能、修复 Bug 或重构时，把它作为独立开发任务处理。
