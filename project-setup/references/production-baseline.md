# 生产基线

本文件定义新项目的共同工程底线。一般实现细节可根据项目实际能力裁剪，但有可执行源码时五类静态质量硬门禁不可裁剪；只能选择适配的分析器并明确范围。不得把未实现或未验证的能力描述成已具备。除无可执行源码的静态质量门禁外，若某项确实不适用，在 Spec 或验证记录中写明理由。

## 1. 最小架构

先围绕一个可运行的业务/用户路径组织代码，再扩展目录。默认保持：

- **职责分层**：入口/传输层负责协议，应用层编排用例，领域层表达规则，基础设施层实现外部适配；小项目可以合并物理目录，但不能混淆职责。
- **模块内聚**：同一能力的行为、类型和测试放在相邻位置，避免按“所有 controller / service / utils”机械分散简单功能。
- **边界明确**：跨模块通过函数、接口、事件或明确数据结构通信，不读写其他模块内部状态。
- **依赖单向**：策略依赖抽象或稳定内核，外部适配依赖接口；禁止循环依赖和领域层反向依赖框架细节。
- **配置分离**：环境差异通过集中、可验证的配置进入系统，业务代码中不散落环境判断和硬编码端点。
- **最少抽象**：没有第二个真实用例时，不提前创建通用框架、万能基类、仓储层或插件系统。

目录和命名必须表达实际职责。出现 God Class、万能 `utils`、跨层访问、隐式全局状态或复制规则时，先在测试保护下做最小重构。

## 2. Docs as Code

初始化时创建并填写真实内容：

```text
docs/
├── architecture.md
├── architecture/
│   ├── maintenance.md
│   ├── diagram-provider.yaml
│   └── changes/
│       └── YYYY-MM-DD-bootstrap.md
├── specs/
├── plans/
└── decisions/
```

- `architecture.md`：系统目标与上下文、模块边界、依赖方向、公共入口、核心数据流、配置与运行边界、外部依赖、信任边界。只描述当前真实实现。`architecture/maintenance.md`、`diagram-provider.yaml` 和 `changes/` 按架构治理契约承载后续 Agent 按需加载的维护规则、可替换绘图 provider 和语义变更历史。
- `specs/<feature>.md`：复杂功能的 Goal、Scope、Non-goals、行为/接口、约束/兼容性和可验证验收标准。初始化时保存 bootstrap Spec。
- `plans/<feature>.md`：可逐项实现、测试和验证的步骤、状态、涉及模块、接口/数据/配置变化以及 QA 顺序。初始化时保存 bootstrap Plan。
- `decisions/<number>-<slug>.md`：记录影响长期维护的重要决策、上下文、备选项、结果和后果。技术选择或边界没有长期影响时不要为数量而写 ADR。

不要创建内容为空的文档、虚假占位说明或永远不会维护的目录索引。代码改变边界、公共接口、核心流程、数据流、配置或部署拓扑时，同一变更中同步文档。历史决策由 ADR 保留，代码历史交给 Git，不在架构文档中累积过期版本。

## 3. 配置、依赖与可复现性

- 明确运行时和工具链版本；使用项目生态认可的版本文件或 manifest 约束。
- 遵循所选生态对锁文件的标准：提交工具生成且具有真实依赖解析、构建或可复现语义的锁文件；存在此类锁文件时，CI 和本地使用相同包管理器及冻结/锁定安装模式。只有不存在可锁定依赖图且生态也不产生有意义锁文件时才标记 `[N/A]`。不要手工创建只有注释或占位内容的空锁文件。
- 仅添加当前垂直切片需要的依赖，优先标准库和已有生态能力。
- 配置在单一入口加载、校验并转换成内部类型；启动时对缺失或非法核心配置明确失败。
- 需要环境变量时提交无秘密的 `.env.example`，写明变量语义、是否必需和安全默认值；真实 `.env`、密钥、证书和本地凭证进入 `.gitignore`。
- 提供从干净 checkout 到安装、开发、测试、构建和运行的可复制命令。
- 不把本机绝对路径、编辑器缓存、生成物或个人配置写入仓库。

依赖或生成器的版本、支持周期、安全状态容易变化时，以当前官方文档、官方发布记录或包注册表为准，不依赖记忆猜测。

## 4. 接口与错误契约

跨模块、外部 API、事件、命令输入和持久化数据必须有明确契约及验证边界。外部输入默认不可信。

有 JSON 外部接口时，使用稳定、非敏感的错误形状，例如：

```json
{
  "code": "INVALID_INPUT",
  "message": "Input is invalid"
}
```

内部错误保留原始原因、完整堆栈和定位所需上下文；当执行需要跨步骤、模块或外部边界关联时同时保留 `trace_id`。每个错误都必须被以下方式之一显式处理：

- 在当前边界恢复并记录结果；
- 转换为该层定义的错误并保留 cause；
- 记录足够上下文后向上抛出；
- 直接向上抛出交给明确的统一边界处理。

禁止空 `catch`、裸 `except`、丢弃错误、用 `any`/ignore/nolint 掩盖类型或规则问题，以及在核心操作失败时返回成功。

## 5. 可观测性

有运行期请求、后台任务、外部调用、持久状态或多步骤操作时，可观测性随第一个垂直切片交付，而不是上线前补做。日志使用项目生态的结构化实现，至少能表达：

```json
{
  "timestamp": "...",
  "level": "INFO",
  "trace_id": "...",
  "message": "...",
  "context": {}
}
```

- `DEBUG`：本地诊断所需细节；生产环境默认不制造噪音。
- `INFO`：请求/任务入口、出口和关键业务状态变化。
- `WARN`：发生异常但已恢复、重试或降级。
- `ERROR`：操作失败、数据风险或需要人工关注。

对需要跨步骤、模块或外部边界关联的请求、命令或后台任务生成关联标识，并在相关模块、DB、Cache、MQ 和外部调用之间传递。记录实际存在的外部调用耗时、状态、重试、降级、慢操作和错误位置。日志必须支持标准输出采集或项目约定的落盘方式。

对于没有外部调用、持久状态、重试或多步骤工作的确定性单进程命令，稳定的 stdout/stderr 与退出码已经完整表达可观察结果时，可以在架构与 QA 中将运行日志和 `trace_id` 标记为 `[N/A]` 并说明理由；不要为了形式完整引入闲置日志设施。

不得记录密码、Token、Cookie、密钥、完整支付/身份数据或未经脱敏的敏感 payload。日志应足以重建一次执行路径，但不得重复打印无诊断价值的信息。

## 6. 数据、并发与外部系统

只有项目实际涉及相关边界时才引入机制，但设计时必须明确失败语义：

| 风险 | 需要回答的问题 | 常见机制 |
|---|---|---|
| DB 写入 | 哪些变化必须原子提交？失败如何回滚？ | transaction、约束、迁移与 rollback |
| 并发更新 | 谁拥有状态？冲突如何发现？ | 乐观锁、悲观锁、原子操作 |
| 重复请求 | 相同意图会否被重复执行？ | idempotency key、唯一约束、去重 |
| MQ 消费 | 至少一次投递如何处理？ | 幂等 handler、去重、ack/nack、DLQ |
| 网络调用 | 多久失败？哪些错误可重试？ | timeout、有限 retry、backoff、jitter |
| 部分成功 | 已完成步骤如何补偿？ | 状态机、补偿动作、可恢复记录 |
| 服务重启 | 中间状态能否恢复？ | 持久化 checkpoint、幂等恢复 |
| 数据迁移 | 新旧版本如何兼容？ | expand/contract、备份、回滚验证 |

重试必须有上限、退避和明确的可重试错误集合；非幂等操作不得盲目重试。外部依赖需要适当的 timeout。只有真实风险和运行规模支持时才加入 circuit breaker、fallback 或复杂状态机。

## 7. 安全默认值

至少检查：

- 所有外部输入的类型、长度、格式、允许值和资源上限；
- 身份认证与授权位置，以及默认拒绝策略；
- SQL、命令、模板和路径参数化，避免注入和路径穿越；
- Web 场景的 XSS、CSRF、SSRF、CORS、Cookie 与安全响应头；
- 安全的序列化格式和反序列化白名单；
- 最小权限的文件、数据库、网络和云权限；
- Secrets 只从受控配置来源注入，不写入代码、镜像、日志或测试快照；
- 依赖来源、锁定、许可证和漏洞检查；
- 错误响应不泄露堆栈、内部路径或敏感上下文。

开发环境便利配置不得成为生产默认值。测试用密钥必须明显无效且不能与真实凭证混淆。

## 8. 质量入口与 CI

使用生态惯例提供清晰命令，名称可适配工具链，但职责必须可发现：

```text
format / format-check
lint
typecheck 或 static-analysis
test-unit
test-integration
test-e2e
test-regression
test 或 test-all
build
verify / qa
```

`verify`/`qa` 是本地聚合入口，按快速失败顺序运行非变更型格式检查、静态检查、五类（六项可观测值）静态质量硬门禁、完整测试和 build。格式化写入命令与 CI 使用的格式检查命令分开。

有可执行源码的项目必须把以下五类（六项可观测值）作为硬门禁，并在规范质量配置或 `docs/quality-gates.md` 中记录指标口径、范围、排除项、工具/版本、命令和阈值：

```text
圈复杂度：每个函数/方法 <= 10；超限数量 = 0
重复代码率：<= 5%
循环依赖数量：= 0
Dead Code：= 0 个生产发现
超长函数：每个函数/方法 <= 80 个逻辑源码行；超限数量 = 0
超大文件：每个生产源码文件 <= 500 行；超限数量 = 0
```

CI 只编排这些仓库内命令；存在有意义锁文件时使用冻结/锁定安装。不要在 CI YAML 中重新实现另一套测试逻辑。其他覆盖率、Secret 扫描、SAST 和依赖漏洞检查按项目风险接入，但不能省略上述五项硬门禁；阈值不能为了通过而降低或跳过。分析器缺失、命令失败、阈值违反、报告过期或结果无法复核时标记 `[FAIL]` 或 `[BLOCKED]`。没有可执行源码时才允许以证据标记 `[N/A]`。

## 9. 保持简单和可演进

遵循：

`Make it work → Make it right → Make it fast`

- 性能优化建立在基准、profile 或真实指标上。
- 先通过接口和测试保护边界，再做必要重构。
- 一次只完成一个可验证切片，避免大批量生成后统一排错。
- 保持向后兼容；API、Schema 或公共包变化需要迁移与消费者分析。
- 删除代码前搜索引用和生成/反射入口。
- 不为未来可能性预建复杂抽象，也不在已知结构问题上继续堆补丁。
